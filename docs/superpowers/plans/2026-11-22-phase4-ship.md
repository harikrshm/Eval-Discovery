# Phase 4 "Ship" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the eval flywheel portable and measurable: an export endpoint and an `evalgate` command-line gate (with a GitHub Action, an example folder and a repo CI workflow incl. real-Postgres tests), an honest simulation (deterministic mock mode plus a small real-Groq run) with a generated results page, a metrics script, a demo script and a case study, and the Phase 3 carry-overs (fail-fast verification, bounded retries on request routes, optional token pacing, small fixes, zero lint errors).

**Architecture:** Two new top-level packages, `evalgate/` (suite loading, runner, CLI; imports only `backend.core` and `backend.groq_client`, never FastAPI or SQLAlchemy) and `simulation/` (fake model client, scenarios, in-process app driver, the two arms, run and report CLIs). The simulation drives the real FastAPI app through `TestClient` on in-memory SQLite and runs the worker inline; the model seam is the `backend.groq_client.client` object. Backend changes are confined to `groq_client`, the request routes, `core/promotion`, `db/reconcile`, the replay handler, one new export route and two small fixes.

**Tech Stack:** Python (FastAPI, SQLAlchemy, Alembic, Groq), React 19 + Vite + Vitest, GitHub Actions (YAML), PyYAML for workflow tests.

**Spec:** `docs/superpowers/specs/2026-11-22-phase4-ship-design.md` (the addendum, sections 1-13; **wins** where it differs), the main spec `2026-11-21-agent-ready-eval-flywheel-design.md` (§9, §11, §12, §13) and the Phase 3 addendum. Branch `feat/phase4-ship` (cut from the unmerged `feat/phase3-evolve`).

## Global Constraints

- No real network in any test: every model call is faked at `backend.groq_client.client` (or patched at the function under test). The test suite sets `GROQ_SKIP_DOTENV=1` so no test, gate run or mock simulation reads `.env`.
- `evalgate/` must import neither `fastapi` nor `sqlalchemy` (a test imports it in a subprocess and asserts `sys.modules`); `backend.core` stays pure.
- The API key is read only from the environment (`GROQ_API_KEY`) by the gate and never printed, logged, written to a file or included in any report; the placeholder key in `groq_client` is never accepted by the gate.
- Gate exit codes (documented, tested): `0` pass rate >= threshold; `1` below it; `2` usage or invalid suite/prompt; `3` the gate could not run (missing key, any test errored after retries, no runnable tests, every test `not_applicable`). The gate never reports success when it could not run.
- Export format string `eval-discovery.suite`, version `1`; the export contains no results, transcripts, runs, events or workspace data, only the keys listed in Task 6. The gate runs only tests whose exported `current_verdict` is `"pass"` unless `--all` is given, and says how many it skipped.
- The simulation's success measure is an **independent reference criterion** per scenario, never the criterion the app discovers; both arms use the same scenario prompt, builder model, caps and reference judge; the baseline's prompt rewrite uses `MODEL_JUDGE` (the app's suggester model), customer messages use `MODEL_CHAT`. Every trial records `path` (`loop` | `fallback` | `none`) and a trial that never converges is reported, never dropped. Every results table says "simulated", names N, models and the date, and mock-mode output carries the banner "MOCK MODE: harness test only, the numbers are meaningless." and is never written to `docs/simulation-results.md`.
- Fail-fast verification reuses the existing reason strings ("The fix test did not pass.", "The held-out test did not pass.", "A previously passing test now fails.", "A test could not be run: ...", "A criterion changed during verification."); cancelled jobs get status `failed` and error exactly "Cancelled: verification already failed.".
- `STALE_FIX` becomes exactly "That fix is based on an older prompt. Reject it and suggest a new fix.".
- Bounded retries: request routes (chat, analyze via create-agent, discover, check-pattern) run their model calls with `request_retries(2)`; job handlers keep `GROQ_MAX_RETRIES` (5). Token pacing is opt-in: env `GROQ_TPM_LIMIT` (unset = off), one sliding 60-second window per model, a call waits at most 20 seconds, usage comes from `response.usage.total_tokens` when it is an int, otherwise a characters/4 estimate.
- Keep Phase 1-3 behavior and tests (updated only where behavior deliberately changes); keep accessibility rules in the frontend; the frontend lint baseline becomes ZERO errors in this phase.
- Never read, edit or commit the repo-root `.env`; do not push; commit messages follow `git log` style. Frontend tests run from PowerShell (`cd frontend; npx vitest run <file>`); backend `python -m pytest <file> -q` from the repo root.

## Review Focus

1. **A gate that passes when it could not run:** missing key, a test that errored, zero runnable tests, all `not_applicable`, an exception inside the runner, an empty suite: all must exit 3 (never 0); the key never appears in output (Tasks 8-10).
2. **A circular or unfair simulation:** the reference judge independent of discovery; identical models and caps in both arms; the flywheel's fallback and path recorded; non-converged trials kept; mock numbers never presented as results (Tasks 14-18).
3. **Fail-fast failing a good candidate or leaving work running:** a decisive failure must be based on stored verdicts only; a missing fix/held-out result with a failed job is decisive but a missing regression result is not; cancellation touches only queued replay jobs of that version; a late-running job must not store results for a resolved version; the real-Postgres race test must still pass (Tasks 3-4, 12).
4. **Secrets and data leaks:** export has no results/transcripts/other-workspace data and is workspace-scoped; no tool or test reads `.env`; step summaries and reports contain no key; workflows request least privilege and never echo secrets (Tasks 6, 8-11, 13).
5. **Overclaiming in generated docs and results:** simulated labels, N, models, limitations, mock banner; the docs state that the GitHub Action was not run on GitHub from here (Tasks 17-21).

## Decisions made in this plan (my calls beyond the addendum)

- P1. `evalgate/` and `simulation/` are top-level packages run from the repo root (`python -m evalgate`, `python -m simulation.run`); the Action sets `PYTHONPATH` to the repo root.
- P2. `evalgate --load-dotenv` (off by default) loads `.env` for local convenience; CI and mock runs use the environment only.
- P3. Majority vote for `--repeat K`: a test passes when `passes * 2 > K`; a test is `error` only when every run of it errored.
- P4. The simulation counts model calls through a `CountingClient` wrapper around whatever client is installed (fake or real) and records wall time per trial.
- P5. The preview is two customer messages (builder-written, `MODEL_CHAT`) answered by the agent, then the reference judge; the cap is 12 previews per trial.
- P6. The real simulation run and the real gate run are executed by the controller after review; their results are committed to `docs/simulation-results.md` and quoted in the case study.

### Task 10: `evalgate` command line

**Files:** Create `evalgate/cli.py`, `evalgate/__main__.py`; test `tests/test_evalgate_cli.py`.

**Interfaces — Produces:** `main(argv: list[str] | None = None, env: Mapping[str, str] | None = None) -> int` and `python -m evalgate`.
